# n8n-coding-agent-sandbox
Private sandbox repository for n8n exercise 2 coding-agent workflow.

این مخزن یک محیط ایزوله برای تمرین‌ها و توسعهٔ ورک‌فلوهای مربوط به «کدنویسی عامل» در n8n است. هدف فراهم کردن یک فضای آزمایشی برای تست و ارزیابی تغییرات بدون اثرگذاری روی محیط‌های تولیدی است.

## دکمه خروج
یک قابلیت جدید با نام «دکمه خروج» (Exit Button) به رابط کاربری اضافه شده است تا کاربران بتوانند به‌سرعت از محیط sandbox خارج شوند و به صفحهٔ اصلی یا داشبورد منتقل شوند. در ادامه شرح کامل عملکرد، پیاده‌سازی، امنیت، دسترسی‌پذیری و تست‌ها آورده شده است.

### اهداف طراحی
- امکان خروج امن و آگاهانهٔ کاربر از جلسهٔ فعلی.
- جلوگیری از از دست رفتن داده‌ها با ارائهٔ گزینهٔ ذخیرهٔ خودکار یا اطلاع‌رسانی دربارهٔ تغییرات ذخیره‌نشده.
- ارائهٔ API واضح برای خاتمهٔ جلسه با لاگینگ و احراز هویت مناسب.
- حفظ ایمنی و جلوگیری از سوءاستفاده (مثل خاتمهٔ جلسات دیگر کاربران).

### مکان در رابط کاربری
- مکان پیش‌فرض: نوار ابزار بالای صفحه، سمت راست (نزدیک دکمه‌های ذخیره و اجرا).
- در صفحات ویرایش ورک‌فلو و مشاهدهٔ لاگ‌ها قابل دسترسی است.
- هنگام باز بودن modalهای بحرانی (مثلاً ویرایش در حال انجام) دکمهٔ خروج همچنان قابل‌مشاهده است، اما فشار آن منجر به نمایش modal تأیید می‌شود.

### نحوهٔ استفاده (برای کاربران)
1. کاربر روی دکمهٔ خروج کلیک می‌کند.
2. یک پنجرهٔ تأیید (modal) با متن واضح نمایش داده می‌شود که شامل:
   - پیام هشدار دربارهٔ تغییرات ذخیره‌نشده، و تعداد یا نام آیتم‌هایی که تغییر نکرده‌اند (در صورت امکان).
   - گزینه‌های «لغو» و «خروج».
   - چک‌باکس اختیاری «ذخیرهٔ خودکار قبل از خروج» اگر قابلیت Auto-Save فعال و پیکربندی شده باشد.
3. در صورت انتخاب «خروج»:
   - اگر عملیات‌های اجرای فعالی وجود دارد، از کاربر پرسیده می‌شود که آیا می‌خواهد اجراها را متوقف کند یا منتظر پایان آن‌ها بماند.
   - طبق پیکربندی سیستم، یک درخواست خاتمهٔ جلسه به سرور ارسال می‌شود. این درخواست ممکن است همزمان (synchronous) یا غیرهمزمان (asynchronous) باشد؛ رفتار دقیق در بخش پیاده‌سازی توضیح داده شده است.
   - پس از تأیید موفق، کاربر به صفحهٔ داشبورد یا لیست ورک‌فلوها هدایت می‌شود.

نکته: توصیه می‌شود پیش از خروج، تغییرات مهم را ذخیره کنید تا داده‌ای از دست نرود. اگر Auto-Save فعال است، modal گزینهٔ اجرای ذخیرهٔ فوری را پیشنهاد می‌دهد.

### دسترسی‌پذیری (Accessibility)
- modal تأیید باید نقش role="dialog" و aria-modal="true" داشته باشد.
- فوکوس باید هنگام باز شدن modal به اولین کنترل مهم (مثلاً دکمهٔ خروج/تایید) منتقل شود و پس از بسته‌شدن به عنصر فراخوان قبلی بازگردد.
- کلیدهای کیبورد: Enter برای تأیید، Esc برای لغو (در صورت مجاز بودن)، و تب‌بندی منطقی بین عناصر.
- تمامی متون و دکمه‌ها باید معادل‌های محلی/قابل ترجمه داشته باشند و برای صفحه‌خوان‌ها توصیف مناسب (aria-label) داشته باشند.

### رفتار موردانتظار و سناریوهای هم‌زمانی
- خروج تنها جلسهٔ کاربری فعلی را خاتمه می‌دهد و نباید تغییرات یا داده‌های دیگر کاربران را تحت‌تأثیر قرار دهد.
- اگر اجرای طولانی‌مدت یا پردازشی در حال اجرا باشد، سه گزینه ممکن است وجود داشته باشد:
  1. توقف فوری (force stop): عملیات بلافاصله لغو می‌شود؛ در این صورت باید پیامدهای ممکن (دادهٔ نیمه‌تمام) مستندسازی شود.
  2. درخواست لغو (graceful cancel): سرور دستور لغو را ارسال و عملیات پس از پاکسازی خاتمه می‌یابد؛ پاسخ ممکن است async باشد.
  3. منتظر ماندن تا پایان: کاربر منتظر می‌ماند تا اجرای جاری تمام شود.
- برای جلوگیری از race condition هنگام فراخوانی همزمان پایان جلسه از چند تب یا از چند کلاینت، API باید idempotent باشد یا مکانیزم قفل/نسخه‌گذاری (optimistic locking) داشته باشد.

### API و مشخصات فنی
پیشنهاد پیاده‌سازی RESTful endpoint و رفتار آن:
- مسیر پایه: POST /api/sessions/{sessionId}/terminate
- روش: POST یا DELETE (POST با body برای پارامترهای بیشتر مانند action preferred پیشنهاد می‌شود)
- هدرهای لازم:
  - Authorization: Bearer <JWT یا token>
  - X-CSRF-Token: <csrf_token> (برای درخواست‌های از مرورگر)
- بدنهٔ نمونه (application/json):
  {
    "workflowId": "<workflow-id>",
    "force": false,           // true برای توقف فوری
    "saveBeforeExit": true    // درخواست برای ذخیرهٔ خودکار قبل از خروج
  }
- پاسخ‌ها:
  - 200 OK: خروج موفق و نهایی (synced)
    {
      "status": "terminated",
      "sessionId": "...",
      "redirectTo": "/dashboards"  // هدف پیشنهادی
    }
  - 202 Accepted: درخواست لغو پذیرفته شد؛ عملیات در پس‌زمینه ادامه دارد
    {
      "status": "cancel_in_progress",
      "operationId": "op-12345"
    }
  - 400 Bad Request: ورودی نامعتبر
  - 401 Unauthorized: کاربر احراز هویت نشده
  - 403 Forbidden: کاربر اجازهٔ خاتمه این جلسه را ندارد
  - 404 Not Found: جلسه یا ورک‌فلو یافت نشد
  - 409 Conflict: عملیات در حال انجام که مانع از خاتمه فوری است
  - 500 Internal Server Error: خطای سمت سرور

رویدادهای پیشنهادی که باید منتشر/لاگ شوند:
- exit_initiated (شامل userId, sessionId, workflowId, clientIp)
- exit_confirmed (شامل نتیجهٔ نهایی)
- exit_cancelled (در صورت لغو توسط کاربر)
- exit_error (جزئیات خطا و stacktrace در لاگ سطح مناسب)

برای عملیات‌های async، ارائهٔ یک endpoint برای بررسی وضعیت عملیات پیشنهاد می‌شود:
- GET /api/operations/{operationId}
  - بازگرداندن وضعیت: pending, in_progress, succeeded, failed

اطمینان از idempotency: اگر کاربر چندین بار درخواست خاتمه را ارسال کند، عملیات نباید منجر به خطا یا وضعیت نامشخص شود؛ از operationId یا قفل سمت سرور استفاده کنید.

### امنیت و مجوزها
- تنها کاربر صاحب جلسه یا کاربران با دسترسی مناسب (مثلاً admin) باید بتوانند جلسه را خاتمه دهند.
- اعتبارسنجی توکن‌ها و بررسی scope/claims ضروری است.
- محافظت در برابر CSRF برای درخواست‌های از مرورگر (ساب‌دامین‌ها، CORS تنظیم صحیح).
- محدودیت نرخ (rate limiting) برای جلوگیری از سوءاستفاده از API خاتمه جلسه.
- حرکت به سمت تامین least privilege: کاربران عادی فقط روی جلسات متعلق به خود حق خاتمه دارند.
- لاگ‌برداری امن: اطلاعات حساس (مثل توکن‌ها) نباید در لاگ ثبت شوند.

### پیاده‌سازی در کلاینت
- قبل از ارسال درخواست خاتمه، اگر Auto-Save فعال است و کاربر درخواست ذخیرهٔ خودکار کرده، ابتدا درخواست ذخیره ارسال شود و در صورت موفقیت ادامه دهد.
- در صورت انتخاب force=true، نشان دادن هشدار واضح دربارهٔ پیامدها (ممکن است داده نیمه‌تمام بیاید).
- نمایش پیام وضعیت به کاربر: در حال پردازش، با موفقیت خاتمه یافت، یا خطا رخ داد.
- در حالت 202 Accepted، کلاینت باید امکان پیگیری وضعیت عملیات را داشته باشد (poll یا subscription بر websocket/notifications).

### لاگینگ و Audit
- لاگ‌ها باید ساختاریافته (JSON) باشند و فیلدهای حداقل زیر را شامل شوند:
  - timestamp
  - level
  - event (مثلاً exit_initiated)
  - userId
  - sessionId
  - workflowId
  - clientIp
  - operationId (در صورت وجود)
  - outcome / error
- سیاست نگهداری لاگ براساس قوانین حریم خصوصی و نیازهای audit تعیین شود.

### نکات برای توسعه‌دهندگان
- رویدادهای مرتبط با دکمه خروج باید به‌صورت واضح لاگ شوند (مثلاً: exit_initiated، exit_confirmed، exit_cancelled).
- پیش از نهایی‌سازی خروج، مکانیزمی برای اطلاع‌رسانی به ماژول‌های در حال اجرا فراهم کنید تا امکان ذخیرهٔ وضعیت یا پاکسازی منابع وجود داشته باشد.
- پیشنهاد پیاده‌سازی: نمایش modal تأیید با callbackهای واضح برای ذخیرهٔ خودکار یا متوقف‌سازی امن اجراها.
- API باید تصدیق و مجوز را به‌درستی بررسی کند و پاسخ‌های واضح ارسال کند. برای عملیات‌های غیرهمزمان از کد 202 و operationId استفاده شود.
- بررسی حالات multi-tab و idempotency و اعمال قفل یا نسخه‌گذاری منطقی سمت سرور.
- اضافه کردن feature flag برای فعال/غیرفعال کردن قابلیت در محیط‌های مختلف (مثلاً DISABLE_EXIT_BUTTON=true در prod یا برای آزمایش).

### تجربه کاربری و متن‌ها (متن پیشنهادی برای modal)
- عنوان: «خروج از محیط آزمایشی»
- متن: «آیا مطمئن هستید می‌خواهید از این جلسه خارج شوید؟ تغییرات ذخیره‌نشده ممکن است از دست برود.»
- گزینه‌ها: «لغو» (بازگشت)، «خروج» (تأیید)، چک‌باکس: «ذخیرهٔ خودکار تغییرات قبل از خروج» (در صورت فعال بودن)

### تست و اعتبارسنجی
تست‌ها باید شامل موارد زیر باشند و در سطح Unit / Integration / End-to-End پیاده‌سازی شوند:
- Unit tests:
  - تابع ساختن payload برای API ورودی‌های معتبر/نامعتبر
  - منطق modal و callbackها
  - تصمیم‌گیری برای force=true یا saveBeforeExit
- Integration tests:
  - فراخوانی endpoint terminate با توکن معتبر و نامعتبر
  - سناریوهای 200/202/403/404/500
  - تست idempotency: ارسال چندبارهٔ درخواست خاتمه
- End-to-End tests (با ابزارهایی مثل Playwright یا Cypress):
  - کاربر با تغییرات ذخیره‌نشده روی دکمه خروج کلیک می‌کند و با لغو هیچ تغییری اتفاق نمی‌افتد.
  - کاربر خروج را تأیید می‌کند و پس از آن هدایت انجام می‌شود.
  - سناریوی وجود اجرای طولانی: انتخاب توقف فوری یا منتظر ماندن و مشاهدهٔ پیام‌های مناسب.
  - تست دسترسی‌پذیری: tab order، aria attributes، عملکرد Esc/Enter.
- Load / Security tests:
  - تست محدودیت نرخ روی endpoint خاتمه جلسه.
  - تست تزریق و پالایش مقادیر ورودی.

موارد تست نمونه:
- تست اینکه کلیک روی دکمه خروج بدون تأیید (لغو) هیچ تغییری ایجاد نکند.
- تست اینکه با تأیید خروج و saveBeforeExit=true، ابتدا ذخیره انجام شده و سپس جلسه خاتمه یابد.
- تست اینکه یک کاربر غیرصاحب جلسه نتواند جلسهٔ دیگران را خاتمه دهد (403).
- تست هم‌زمان: دو تب هم‌زمان درخواست خاتمه ارسال می‌کنند، نتیجه باید پایدار و قابل پیش‌بینی باشد.

### نکات عملیاتی و بهره‌برداری
- مانیتورینگ و آلارم برای خطاهای مکرر در endpoint خاتمهٔ جلسه.
- استفاده از SLO/SLI برای زمان پاسخ‌دهی خاتمهٔ جلسه (برای درخواست‌های sync) و برای عملیات‌های async پایش وضعیت operationId.
- اطلاع‌رسانی در لاگ‌ها برای تیم پشتیبانی با لینک به operationId جهت بررسی سریع.

دلیل این تغییر: مستندسازی قابلیت جدید برای توسعه‌دهندگان و کاربران تا استفاده و نگهداری این ویژگی ساده‌تر، ایمن‌تر و قابل آزمون‌تر باشد. نسخهٔ اصلاح‌شده شامل جزئیات امنیتی، API، دسترسی‌پذیری، لاگینگ و سناریوهای تستی است تا پیاده‌سازی عملی و امن تضمین شود.
